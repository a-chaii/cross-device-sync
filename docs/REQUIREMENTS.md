# WatchSync 需求文档（PRD）

> 对应实现：v11.5
> 技术细节见 `docs/TECH.md`；iOS 落地见 `docs/IOS_PROMPT.md`、`docs/IPAD_AGENT_PROMPT.md`；算法见 `docs/ALGO.md`；视觉见 `docs/DESIGN.md`
> 文档定位：**说明「要什么」和「不要什么」**，不描述实现细节

---

## 1. 背景与目标

现状：Android 端通过 Hook 采集手表/耳机电量，经 `PUT /:key` 上报到 Cloudflare Worker，数据落 Workers KV；Web 看板负责可视化。数据此前按**条数**（2000 点）裁剪，没有时间维度——导致「半年前的点和昨天的点混在一起」，看板和原生端都只能拿到一堆无意义的历史。

本次改造目标：

| 编号 | 目标 | 判定标准 |
|---|---|---|
| G1 | 历史数据**只保留最近 7 天** | 任意时刻查询，都不返回 7 天前的点 |
| G2 | 7 天是**产品硬约束**，不是可配置项 | 代码常量化、无环境变量开关、`/health` 可自证 |
| G3 | 原生端（iOS）能**直接拿历史**，不必模拟看板登录 | 提供 token 鉴权的纯 JSON 端点 |
| G4 | 删除设备时**不留垃圾** | 主记录与历史键同生命周期 |

---

## 2. 角色与端

| 端 | 角色 | 能力 |
|---|---|---|
| Android 采集端 | 生产者 | 读第三方设备电量（Hook）、`PUT /:key` 上报 |
| Web 看板 | 消费者 | cookie 登录、曲线/表格、多设备总览 |
| iOS App + Widget（本期新增） | **纯消费者（只读）** | 只读 `/list`、`/:key`、`/dash/hist`；**不上报、不写入** |
| Worker + KV | 服务端 | 存储、裁剪、鉴权、下发 |

---

## 3. 硬约束（不可协商）

| 编号 | 约束 | 理由 |
|---|---|---|
| C1 | 历史保留 **7 天（604800000 ms）** | 用户明确要求「只存最近一周就够够了」 |
| C2 | 保留策略**写死在代码**，不做成环境变量 | 这是产品定义，不是运维旋钮；避免线上被改出不一致 |
| C3 | `x-sync-token` **不得进入任何客户端源码/仓库** | 泄露即等于全量读写权限，包括 DELETE |
| C4 | 看板密码 `DASH_PWD` **不得内置进原生 App** | 原生端已有专用端点，无需求助 cookie 流程 |
| C5 | 采样点必须**按时间单调递增** | 裁剪算法与前端绘图都依赖该不变量 |
| C6 | 值未变化（`level` 与 `charging` 同时相同）**不落点** | 防止轮询缓存值被伪装成「持续上报」 |

> C2 的补充说明：`/health` 返回 `histRetentionMs` / `histRetentionDays`，**客户端应读取它而不是硬编码 7 天**——将来若调整（虽然按 C2 不该调），客户端不会静默错。

## 4. 功能需求

### 4.1 上报（生产者）

- FR-1.1 上报接口：`PUT /:key`，body `{"value": <任意 JSON>}`，鉴权 `x-sync-token`。
- FR-1.2 单次 body ≤ 24 KB，超限返回 `413`。
- FR-1.3 支持乐观并发：带 `x-sync-base-version` 且与服务端版本不符返回 `409`，响应体回带 `current`。
- FR-1.4 每次成功写入**顺带记一个采样点**，采样失败不得影响主写入（异步、失败静默）。
- FR-1.5 采样点时间优先用上报的 `ts`（毫秒）；`ts` 不合理（≤1e12、超前 5 分钟、早于 60 天）时回退服务端时间。
- FR-1.6 上报「同值」被跳过时，`PUT` 仍应返回 200（版本号照常 +1），只有历史不增点。

### 4.2 读取（消费者）

- FR-2.1 **Web 看板**：`GET /dash` 登录（`DASH_PWD` → cookie），`GET /dash/data?key=&range=` 取数据。默认窗口改为近 7 天，下拉项为 1h/3h/6h/24h/3d/7d/全部；**移除「近 30 天」**。
- FR-2.2 **原生端历史**：`GET /dash/hist?key=&range=`，`x-sync-token` 鉴权，返回 `{key,label,hist[],total,now,retentionMs}`。
  - `hist` 升序、已按 `range` 与 7 天窗口双重裁剪；
  - `range=0` 或省略语义为「保留窗口内全部」（即最多 7 天），**不是**「有史以来全部」；
  - `range` 超过 7 天自动夹紧；
  - key 不存在时返回 `200` + 空 `hist`（便于客户端区别「无数据」与「请求错误」）。
- FR-2.3 **列表**：`GET /list?prefix=` 返回键名 + `updatedAt`，**过滤 `@` 前缀内部键**，上限 100 条。
- FR-2.4 **单条**：`GET /:key` 返回主记录，附 `x-sync-version` / `x-sync-updated` 响应头；`HEAD` 仅取头。
- FR-2.5 **健康检查**：`GET /health` 无需鉴权，返回服务名、时间、`histRetentionMs`、`histRetentionDays`。

### 4.3 保留与清理

- FR-3.1 写入时剪掉窗口外旧点（按 `t` 单调性从头部扫描 + 一次 `splice`）。
- FR-3.2 读取时同样以 `now - 7d` 为下界，**双保险**：即使写入侧漏剪，读取侧也不会吐旧数据。
- FR-3.3 `HIST_LIMIT = 2000` 降级为兜底（防异常高频写入撑爆单 value），正常 7 天窗口远达不到。
- FR-3.4 `DELETE /:key` 必须**同时清理 `@hist:<key>`**，避免孤儿键累积。
- FR-3.5 内部键（`@hist:*`）不得通过任何接口对外可见或写入。

### 4.4 鉴权与安全

| 通道 | 凭据 | 适用 | 不适用 |
|---|---|---|---|
| token | 请求头 `x-sync-token` = `SYNC_TOKEN` | 上报、`/list`、`/:key`、`/dash/hist` | 看板页面 |
| cookie | `POST /dash` 校验 `DASH_PWD` → `ws_dash` cookie | `/dash`、`/dash/data` | 原生端（C4） |
| 无 | — | `/`、`/intro`、`/health`、`OPTIONS` | 其余全部 |

- FR-4.1 密码/cookie 比较用等时比较，cookie 值为 `sha256('ws-dash-v1|' + pwd + '|' + SYNC_TOKEN)`。
- FR-4.2 `/dash/hist` 拒绝 `@` 开头 key，返回 `400 invalid_key`。
- FR-4.3 所有对外 JSON 响应（含错误）应带 CORS 头，`Access-Control-Expose-Headers` 暴露 `x-sync-version` / `x-sync-updated`。

### 4.5 键名与设备识别

- FR-5.1 key 允许字符：`a-zA-Z0-9 . _ : - /`，长度 1–256。
- FR-5.2 「设备键」判定（决定是否进看板设备列表）：
  - `watch/battery`
  - `dev/<4–32 位 hex>`
  - `<小写字母开头的 1–21 位标识>/battery`
- FR-5.3 展示名优先级：上报 `value.name` → 按 key 推导（`dev/<hex>` 取后 6 位）→ 原样 key。

### 4.7 iOS 桌面小组件（本期新增）

数据来源：App Group 共享缓存（App 拉取后写入），Widget 亦可自行短暂联网刷新。

| 尺寸 | 必须显示 | 说明 |
|---|---|---|
| `.systemSmall` | 最多 3 台设备的**当前电量** + 充电图标 + 相对更新时间 | 按 `updatedAt` 倒序 |
| `.systemMedium` | 每台设备的**预计续航**（按放电速率外推） | 充电中显示「充电中 · 已充 X」；`c` 缺失但电量在涨显示「推测充电」；样本不足/稀疏/>720h 显示「数据不足」；**没有「电量稳定」这个状态** |
| `.systemLarge` | 中号内容 + **最近 24 小时曲线** | 曲线用 `Canvas`/`Path` 自绘，`l==nil` 断开，单点画点不画线 |

- FR-7.1 刷新：`Timeline` 策略 `.after(+15min)`；App 前台刷新成功后 `reloadAllTimelines()`。
- FR-7.2 **离线必须可用**：网络失败时静默使用缓存，组件不得显示错误文本。
- FR-7.3 预计续航必须按固定公式（唯一真源 `ALGO.md`，摘要见 `IOS_PROMPT.md` §6 / `IPAD_AGENT_PROMPT.md` §5），**样本不足时宁可不给结论**；不许各端自行实现。
- FR-7.4 预计续航是粗估，UI 与 README 均需注明「线性外推，仅供参考」。

### 4.8 展示要求

- FR-6.1 曲线横轴为时间，缺测段不连线（避免直线伪装成连续采样）。
- FR-6.2 表格「模块」列显示 `mv`，用于分辨某段曲线由哪版 Hook 采集。
- FR-6.3 超过 2 小时未变化的值需灰显并提示「可能是缓存值」。

## 5. 非功能需求

| 编号 | 项 | 要求 |
|---|---|---|
| NFR-1 | 存储上限 | 单设备 7 天窗口内实测 5–12 KB（约 200–400 点）；KV 单 value 上限 25 MB，**瓶颈在每日写入配额而非容量** |
| NFR-2 | 读放大 | 看板总览最多展开 12 台设备、单设备最多下发 900 点，防止 KV 读次数爆炸 |
| NFR-3 | 写入延迟 | 历史采样必须异步（`ctx.waitUntil`），不得增加 `PUT` 响应时间 |
| NFR-4 | 兼容性 | 老客户端不带 `ts` / `mv` / `name` 时功能不降级，仅少字段 |
| NFR-5 | 可观测 | `/health` 暴露保留策略；Worker observability 开启 |
| NFR-6 | 一致性 | 时间窗三处（写剪枝、读过滤、range 夹紧）必须同源，禁止各写一份常量 |

## 6. 不在本期范围（Out of Scope）

- 跨设备**双向**同步（当前是「多端写入同一 key，后写覆盖」）。
- 历史数据的**长期归档**（用户明确只要 7 天；要归档就得换存储，不是 KV 的活）。
- 用户体系 / 多租户（单 `SYNC_TOKEN` + 单 `DASH_PWD`）。
- iOS 读取第三方蓝牙设备电量（系统未开放，详见 §7-D1）。
- iOS **上报**任何数据（已裁定：iOS 纯只读接收端）。
- 图表导出、推送告警。

## 8. 验收标准

| 编号 | 场景 | 通过条件 |
|---|---|---|
| AC-1 | 写入 8 天前的点后再写新点 | 8 天前点被剪，`@hist:` 数组只含 7 天内 |
| AC-2 | 历史全部过期后写新点 | 数组只剩 1 个新点 |
| AC-3 | 写入 2005 个点（模拟异常高频） | 兜底裁到 2000 |
| AC-4 | `GET /dash/hist?range=0` | 只返回 7 天内，且 `retentionMs=604800000` |
| AC-5 | `range=90d` | 被夹到 7 天，不返回更早数据 |
| AC-6 | 无 token 调 `/dash/hist` | `401`，且带 CORS 头 |
| AC-7 | `key=@hist:xxx` | `400 invalid_key` |
| AC-8 | `DELETE /:key` | `@hist:<key>` 同步消失 |
| AC-9 | 看板下拉 | 无「近 30 天」，默认选中 7 天 |
| AC-10 | `ts` 为秒级时间戳（1.7e9） | 被判定不合理，回退服务端时间 |
| AC-11 | 连续两次上报同 `level`+`charging` | 历史不增点，`PUT` 仍 200 |

> 覆盖情况：AC-1~AC-8 由自动化用例覆盖（TTL 12 条 + 路由 23 条，全绿）；AC-9 用 `grep -c '2592000000'` 实测为 `0`（页面已无 30 天选项）；AC-10/AC-11 为逻辑约束，随上述用例间接覆盖。

## 9. 发布说明要点

1. 历史保留期由「2000 点」改为「最近 7 天」，**更早数据会被逐步丢弃**，不可恢复。
2. 看板「全部历史」现在指「最近 7 天」，下拉移除 30 天选项。
3. 新增 `GET /dash/hist`，供原生端直接取历史（需 `x-sync-token`）。
4. `DELETE` 现在会连历史一起删——**误删无法恢复**。
