# 预测算法白皮书（唯一实现）

> 版本：v11.5（对应 commit `8e55680`）
> 代码位置：`src/dash.ts` 前端脚本段（`isCh` / `annotate` / `olsRate` / `ptsOf` / `cyclePts` / `sparseOf` / `statOf` / `chgStat` / `drawBars`）
> 单测：页面产物断言 42 条 + 充电算法 56 条 + 算法回归 27 条（`/tmp/db6/*`，见 `docs/TECH.md` §10.5）

---

## 0. 为什么有这份文档

iPad 端正在自己实现一遍续航预测，这会立刻产生第二套口径：同样的数据，Web 说「满电 39 小时」，iPad 说「28 小时」，用户没法判断谁对。

**从本文件起，预测算法只有一份实现，就是服务端看板里这一份。** 其他端要么照抄本文（含全部阈值与边界分支），要么直接显示「—」。

判定标准很硬：**同样的 `hist` 输入，任何端算出的 `rate` / `life` / `elapsed` / `eta` 必须与本文的校验用例逐位一致**（见 §9）。

---

## 1. 输入契约

只有一种输入：`GET /dash/hist?key=<key>&range=<ms>` 返回的 `hist` 数组，**按 `t` 升序，服务端已裁到 7 天内**。

| 字段 | 类型 | 语义 | 陷阱 |
|---|---|---|---|
| `t` | Int64 ms | 采样时刻 | 单位是**毫秒**，不是秒 |
| `l` | Int? 0–100 | 电量 | 可能为 `null`；**不是** Double |
| `c` | Int? 0/1 | 设备上报的充电标志 | **手表恒为 0**，不可信（见 §4.3） |
| `v` | Int | 该键第几次成功写入 | 会因去重跳号，**不连续** |
| `s` / `m` | String? | 采集来源 / 模块版本 | 调试用，不进 UI |

**不要自己再裁一次 7 天窗口。** 服务端已裁，客户端重复裁只会在时钟偏移时误删数据。

## 2. 处理管线（顺序不能变）

```
hist
 └─ ptsOf()      ① 丢掉 l 为 null 的点  ② 同一毫秒去重（保留先到）  ③ 交给 annotate()
     └─ annotate()  打三个标记：rep / jump / inf
         ├─ cyclePts()  「充满电后」视图：从最后一个 100% 点切起（可选，看板默认开）
         ├─ sparseOf()  稀疏设备判定：默认不画、不统计
         ├─ statOf()    放电侧统计
         ├─ chgStat()   充电侧统计
         └─ drawBars()  小时分布（掉电次数 / 充入百分点）
```

### 2.1 `ptsOf`：两个清洗动作

| 动作 | 规则 | 为什么 |
|---|---|---|
| 丢空值 | `typeof l !== 'number'` 直接跳过 | 无电量的点无法参与任何计算 |
| 同毫秒去重 | `if (a.last.t === h.t) continue;` 只保留**先到**那条 | 模块同一 tick 会连写两次（实测 `11:03:29` 先 79 后 75），两条都留会让曲线同一横坐标「一升一降」，凭空多出一次 4% 掉电，还会把充电段切断 |

> 去重发生在 `annotate` **之前**，所以后续所有统计（放电次数、累计掉电、充电段）都自动受益。

### 2.2 `annotate`：三个标记

```js
rep  = (c === 1 || c === true)                       // 设备自称在充电
jump = |b.l-a.l| >= JUMP && |b.l-c.l| >= JUMP && |a.l-c.l| <= 2   // 孤立尖点
inf  = !rep && prev && (q.l - prev.l) >= 1            // 相对上一个「非尖点」上升
```

语义边界，容易写错的地方：

- `jump` 只在**中间点**上判（首末点不判），且要求前后两点彼此接近（容差 2）——这是为了区分「锯齿」与「真的掉了 10%」。
- `inf` 计算时 `prev` **不推进**尖点，也就是和「最后一个正常点」比。
- `inf` **只表示上升**，不代表「正在充电」。判断「是否在充电」要用 §4 的状态机，不要直接用 `inf`。

### 2.3 `cyclePts`：默认视窗不是 7 天

看板默认只统计**最近一个充电周期**：从倒数第一个 `l >= 100` 的点切起；找不到 100% 就从最后一个 `rep` 点切起；切完剩不到 2 点就退回原始序列。

用户可勾「全部历史」(`S.all`) 关掉这个裁剪。

**iPad 若做「预计续航」，必须明确用的是哪种口径**，否则和 Web 对不上。建议：默认与 Web 一致（充满电后）。

### 2.4 `sparseOf`：稀疏设备

判据：`span >= 2h` 且「间隔 > 1.5h 的空档总时长占 span 比例 > 55%」。

稀疏设备**默认不画曲线、不进统计**（图例里点一下才强制显示）。

## 3. 参数表（全部硬编码，不要「优化」）

| 参数 | 值 | 位置 | 说明 |
|---|---|---|---|
| `JUMP` | 8 (%) | `annotate` | 单次跳变阈值。低于 8 的正常掉电不会被误剔 |
| 尖点缝合容差 | 2 (%) | `annotate` | 前后两点差 ≤ 2 才认作「同一个值被尖点打断」 |
| `inf` 上升阈值 | 1 (%) | `annotate` | ≥1 即视为上升 |
| 回归最小样本 | 3 | `olsRate` | 不足则回退首末差分 |
| 续航显示上限 | 720 h（30 天） | `statOf` | 超过视为外推不可信，**直接不显示** |
| 充电速率最小观测窗 | 180000 ms（3 分） | `chgStat` | 短于此不给速率，避免除零爆表 |
| 满电判定 | `l >= 100` | `chgStat` | 满电不给 ETA |
| 链路判死 | ≥ 2 h 无 `updatedAt` 更新 | `renderCards` | 卡片置灰 |
| 「电量未变」提示 | ≥ 2 h | `renderCards` | 灰字，不判死 |
| 稀疏阈值 | 2 h / 1.5 h / 55% | `sparseOf` | 见 §2.4 |
| 分布图桶 | 24 个 1 小时桶 | `drawBars` | `idx = 23 - floor((now - t) / 3600000)` |

## 4. 充电侧：`chgStat`（v11.5 新增）

这是最容易被各端各自发明的地方，按下面这套状态机写。

### 4.1 分段状态机

```js
prev = null; cur = null; segs = [];
for (q of points) {            // points 已 annotate
  if (q.jump) continue;        // 尖点不参与分段，也不推进 prev
  rise = prev != null && (q.l - prev.l >= 1);
  drop = prev != null && (q.l < prev.l);

  if (cur) {
    if (drop) { cur.t1 = q.t; segs.push(cur); cur = null; }   // 真掉电才收段
    else {                                                    // 持平或上涨 → 续段
      cur.t = q.t; cur.l = q.l; cur.n++;
      if (q.rep) cur.inf = false;                             // 设备亲口承认则不算推断
    }
  } else if (q.rep || rise) {                                 // 起段
    cur = { t0: q.t, l0: q.l, t: q.t, l: q.l, n: 1, inf: !q.rep };
  }
  prev = q;
}
if (cur) { cur.open = true; cur.t1 = cur.t; segs.push(cur); }
```

**三条铁律：**

1. **持平必须续段**。采集端 1–2 分钟报一次，连续几点电量不变是常态。按「上升才算充电」切段，一次完整充电会被切成几十个碎片，「已充时长」每几分钟归零一次。
2. **只有掉电才收段**。不许用「连续 N 点没涨」「超过 X 分钟没变化」这类超时规则——息屏冻结时数据本来就停，超时会把一次正常充电误判成结束。
3. **尖点直接 `continue`**，既不续段也不收段。

### 4.2 派生值

设最后一段为 `last`（`last = segs[segs.length - 1]`）：

| 字段 | 公式 | 成立条件 |
|---|---|---|
| `open` | 循环结束时 `cur != null` | — |
| `elapsed` | `last.t - last.t0` | 仅 `last.open` |
| `curGain` | `last.l - last.l0` | 仅 `last.open` |
| `rate` | `curGain / (elapsed / 3600000)` | `elapsed > 180000` **且** `curGain > 0`，否则 `null` |
| `eta` | `(100 - last.l) / rate * 3600000` | 需 `rate > 0` **且** `last.l < 100`，否则 `null` |
| `gain` | `Σ(seg.l - seg.l0)` 全部段 | — |
| `avgRate` | 对每个闭合段取 `(seg.l - seg.l0) / ((seg.t - seg.t0)/3600000)` 求平均 | 只算 **`open == false`**、`seg.t > seg.t0`、**`seg.l - seg.l0 > 0`** 的段 |

**`elapsed` 绝对不能外推到 `Date.now()`。** 采集端息屏会被系统冻结（不在 Doze 白名单 + `oom_adj=4`），如果按「现在」算，一段停了 5 小时的充电会被写成「已充 8 小时」，越冻越离谱。只算到最后一条数据是保守且诚实的。

**`curGain == 0` 时不要给 `0.00 %/h`。** 报了充电但电量一直没动，速率就是「未知」，给 `null` / `—`。

### 4.3 为什么不用 `c` 字段

手表实测：`l` 从 47 一路涨到 79，`c` 全程为 `0`。宿主 App（`com.heytap.mydevices`）自己就没把充电标志给对，不是采集模块没读。

所以：**`rep` 只作为「确认」用，不能作为「唯一依据」**。没有 `rep` 时靠电量不再下降 + 此前在上涨来推断，UI 必须标「推测充电」或「推断」，不能伪装成事实。

## 5. 放电侧：`statOf`

```js
for (q of points) {
  if (q.jump) { jumps++; continue; }     // 尖点既不算采样也不算掉电
  valid++;
  if (prev) {
    if (q.l < prev.l) { drops.push({t:q.t, from:prev.l, to:q.l, d:prev.l-q.l}); sum += d; maxOne = max(maxOne, d); }
    if ((q.rep || q.inf) && !(prev.rep || prev.inf)) charges++;
  }
  prev = q;
}
span = last.t - first.t;
```

### 5.1 掉电速率：最小二乘回归

```js
// 样本：相邻两点，且两端都不在充电（不是 rep 也不是 inf）
xs.push((r.t - p[0].t) / 3600000);   // 小时
ys.push(r.l);                        // 电量

olsRate(xs, ys):
  if (n < 3) return null;
  slope = Σ(x-x̄)(y-ȳ) / Σ(x-x̄)²;
  if (!isFinite(slope) || slope >= 0) return null;   // 整体在上升 → 不算放电
  return -slope;                                     // 转成正值 %/h
```

**为什么不直接用首末差分**：耳机 `90↔100` 锯齿会让首末差分算出 3.47 %/h（满电 28.8 h），实测真实值约 1.2 %/h。回归 + 剔尖点后回到正常区间。

**充电上升段必须排除**，否则上升斜率混进时间轴，把放电速率摊薄。

### 5.2 回退与钳制

```
rate = olsRate(...) ?? (span > 0 && sum > 0 ? sum / (span / 3600000) : null)
life = rate > 0 ? 100 / rate : null
if (life > 720) life = null        // 超过 30 天不给
```

回退时 UI 在续航数字后加 `~`（表示精度低）；回归可用时不加。**`reg` 布尔值必须跟着传出去**，UI 要靠它决定是否显示 `~`。

### 5.3 其余字段

| 字段 | 含义 |
|---|---|
| `n` | 原始点数 |
| `valid` | 剔噪后的有效点数 |
| `jumps` | 尖点数，UI 显示「剔噪 N」 |
| `sum` | 累计掉电 % |
| `maxOne` | 单次最大掉电 % |
| `avgGap` / `maxGap` / `minGap` | 掉电间隔：相邻两次掉电的时间差 |
| `charges` | 充电次数：`进入 (rep 或 inf)` 的次数，UI 上必须标「含推断」 |

## 6. 小时分布：`drawBars`

两种口径共用一个 24 桶直方图（按「现在」往前 23 小时对齐）：

```
idx = 23 - floor((now - p[b].t) / 3600000)      // 0 = 最早 1 小时，23 = 当前小时
```

| 口径 | 累加 | 颜色 |
|---|---|---|
| 放电（`S.mode = 'dis'`） | `dl < 0` 时 `cnt[idx]++`（**次数**） | 蓝 `rgba(96,165,250,.95) → rgba(59,130,246,.30)` |
| 充电（`S.mode = 'chg'`） | `dl > 0` 时 `cnt[idx] += dl`（**百分点**） | 绿 `rgba(52,211,153,.95) → rgba(16,185,129,.30)` |

约束：`p[b].jump` 跳过；并要求 `!p[b-1].jump`（不拿尖点当基准）；`sam[idx]` 无论增减都计数，用于 tooltip 显示「采样 N 条」。

空态文案必须区分：`近 24 小时没有掉电记录` / `近 24 小时没有充入记录`。

## 7. 卡片与表格的派生字段（别自己起名）

| 字段 | 公式 | 语义 |
|---|---|---|
| `linkTs` | `Date.parse(rec.updatedAt)` | 采集链路最后活动时间（含心跳） |
| `linkDead` | `now - linkTs >= 2h` | 进程大概率被冻结 |
| `since` | 最后一次电量变化的时间 | 电量最后一次真的变了 |
| `stillH` | `now - since`（小时） | ≥ 2h 时显示「链路正常 · 电量 X 未变」 |
| 24h 变化 | `cur.l - 24h前最近点.l` | 显示 `+N%` / `N%` / `—` |
| `sd`（表格） | `q.t - 上次掉电时刻` | 「距上次掉电」 |
| `ct`（表格） | `q.t - 当前充电段 t0`，段外用 `null` | 「已充电多久」 |
| `chg`（表格） | 该点是否在充电段内 | 状态列显示「充电 / 推测充电 / 放电」 |

**`sd` 与 `ct` 的段判定必须与 `chgStat` 完全同一套**（`buildRows` 里复制了同一个状态机），否则表格和统计面板会互相打脸。

## 8. 格式化

| 函数 | 规则 |
|---|---|
| `fmtT(t)` | `hh:mm`，跨天只显示时间不显示日期（看板口径） |
| `fmtDur(ms)` | `<90s` → `N 秒`；`<90min` → `N 分`；`<48h` → `N 时[M 分]`；否则 `N 天[M 时]` |
| 百分比 | 数字紧跟 `%`，无空格；增量为正带 `+` |
| 无值 | 一律 `—`（U+2014），**不要**写 `N/A` / `null` / `--`（电量占位是 `--`，仅限卡片大数字） |
| 推断 | 必须在同一行加可视化标识：`推测充电` / `推断` / `回归` / `~` |

## 9.5 续航速率的长样本口径（v11.7）

`statOf()` 算出的 `rate` 只描述**当前视窗**；续航外推改走长样本 `wideRate(全文点)`：

- 只累加「相邻两点都不在充电（无 `rep`/`inf`）、且确实掉电（`dd > 0`）」的间隔，跨充电周期累加，天然跳过充电上升段与尖点；
- 样本 **≥20 分钟且 ≥2 段**才采纳，否则退回视窗回归（服务端对应 `st.reg=false`，UI 加 `~`）；
- 满电续航 `life = 100 / rate`；按当前电量还剩 `remain = level / rate`（`remainHours`）；`> 720h` 一律不给。

反例（2026-11-06 线上）：11:57 充满，到 14:45 只掉 6%（2.8 小时），短窗口外推 = 49 小时；把 7 天里所有纯放电间隔累加（58% / 21 小时）得 2.76 %/h，续航 36 小时。

客户端不需要知道这些：一律读 `/dash/stats` 的 `display.*` 与 `discharge.*`。

## 10. 禁止事项（违反即返工）

- ❌ 另起一套「预计续航」算法，或把 `240h` 上限、`0.2 %/h 稳定阈值`、首末差分当主算法（那是 v11.1 的旧口径，已废弃）。
- ❌ 用 `c` 字段当唯一充电依据（手表恒为 0）。
- ❌ 用「连续 N 点没涨 / 超时」切分充电段（会把冻结误判成充满）。
- ❌ 把 `elapsed` 外推到 `Date.now()`。
- ❌ 给 `0.00 %/h` 或「0 分钟充满」这类伪精度。
- ❌ 客户端自己剔尖点但阈值不是 8 / 容差不是 2（口径一分叉就再也对不上了）。
- ❌ 把推断值当事实展示（必须标「推测 / 推断 / ~」）。
- ❌ 因为曲线平台就补点、插值、伪造采样。
- ❌ 显示超过 720h 的续航。
